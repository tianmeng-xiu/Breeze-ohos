# Breeze-ohos

> ## ⚠ 上游官方已支持 HarmonyOS NEXT
>
> **上游 Breeze 自 v3.1.0（2026-11-21 发布）起官方支持 HarmonyOS NEXT，并直接发布鸿蒙 HAP 安装包**（`Breeze-ohos-arm64-v3.1.0.hap`，即上游把自家 Flutter 代码编译到 OHOS 产出的官方包）。**本项目与那个官方包不是同一个东西**：
>
> - 上游官方包 = 把上游自家 Flutter 代码编译到 OHOS 产出的 HAP（据上游 `docs/ohos_build.md`：`flutter build hap --target-platform ohos-arm64`）；本项目 = 从 UI 到插件引擎的 **ArkTS（ArkUI）+ Rust 原生重写**，两边代码与产物互不相干。
> - 包名不同（上游 `com.zephyr.breeze.ohos` / 本项目 `com.breeze.ohos`），**可在同一台设备共存安装**，但数据互不相通。
> - 那枚官方包**未签名、仅 arm64、最低 HarmonyOS 5.0.5(17)**，按上游自己的说法需要用目标设备信任的证书与 profile 自签后才能装到零售机，**OpenHarmony 测试证书装不上零售机**。本项目的包同样未签名，安装方式见[装到设备](#装到设备)。
> - 若你只想要「上游 Breeze 的鸿蒙版」，去上游 Releases 拿那枚即可；**本项目存在的意义是原生形态** —— 不背 Flutter 运行时，能力覆盖与取舍不同（逐项差在哪见下文[应用侧与上游 Breeze 的对照](#应用侧与上游-breeze-的对照)）。

HarmonyOS / OpenHarmony 原生漫画阅读器：ArkTS（ArkUI）应用 + Rust 编写的 QuickJS 插件引擎，从 Flutter 版 [Breeze](https://github.com/breeze-project-org/Breeze) 移植而来。插件 ABI、宿主桥接路由、设置页数据契约、配置桶格式等接口事实由上游行为逆向得出，在 ArkTS 与 Rust 里重新实现，未复制上游任何 Dart 源码。

代码按 [GPL-3.0-or-later](LICENSE) 发布，来源与第三方许可见 [NOTICE.md](NOTICE.md)。

现成安装包见[装到设备](#装到设备)（未签名 HAP，可自签，也可在开启开发者模式的设备上用 hdc 装），自己编译见[构建](#构建)。功能并不完整，请先读一遍[已知限制](#已知限制)。

## 功能

插件引擎（本项目的核心）：ArkTS 经 NAPI 调一个 Rust cdylib，Rust 内跑 QuickJS，把上游「插件 = 一个 .cjs 包 + 一组约定函数名」的契约原样搬过来。

- 引擎导出 19 个 NAPI 函数（`init` / `eval` / `selftest` / bundle 调用 / 文件与网络桥接等），重活走 `napi_async_work`，不阻塞 UI 线程。
- 宿主桥接分两层：ArkTS 侧五条路由（应用版本、语言信息、提示、插件配置的存与取），Rust 侧十条原生路由（缓存七条、简繁转换入口、运行时两条）。注入写成单个表达式并做回读全等校验，不匹配就写进诊断。
- 入参契约与上游逐条对齐：插件函数永远收到恰好一个对象参数且必带 `extern` 键。
- 自带三个 rawfile 载荷：`plugin_mgr`（插件索引与下载）、`selftest`（引擎自检）、`real`（端到端验证用的真插件夹具，第三方作品，见 [NOTICE.md](NOTICE.md) §3）。

### 本项目独有或形态不同的部分

上游没有、或实现方式明显不同的：

- **原生插件引擎**：Rust + vendored QuickJS 交叉编译成 `.so`，经 NAPI 暴露接口，缓存、简繁转换入口与运行时共十条路由在 Rust 侧完成。
- **悬浮胶囊底栏 + 滚动时自动收起**：SDK 原生页签控制器没有任何隐藏接口，改用自研滚动监听 + 系统组件的收起动画，并按能力分三档降级。
- **键盘避让观感**：窗口 resize + 容器竖向居中，让搜索记录区的上移量天然等于键盘高度的一半，不吃任何手抄常量。
- **封面飞行转场**：书架 ⇄ 详情、详情 ⇄ 阅读器两两之间，封面作为共享元素双向飞行（飞入必配飞出，退出时先飞回原处再关页），页面本体走淡入淡出配合。上游在详情页是明确禁用这类 Hero 动画的。
- **诊断面板 0–20 号行**：入口 = 「关于」页版本行连点 5 次。这是本项目远程定位问题的主要通道，导出的 JSON 对修 BUG 最有帮助。
- **整站是原生 ArkTS 重写，不是移植壳**：上游自 v3.1.0 起也发鸿蒙 HAP，但那条路是 Flutter 编译到 OHOS（包名 `com.zephyr.breeze.ohos`，未签名、仅 arm64、最低 HarmonyOS 5.0.5(17)，需自行签名才能装到零售机）；本项目是从 UI 到插件引擎的 ArkTS + Rust 原生实现（包名 `com.breeze.ohos`，要求 API 26）。两个包名不同、可共存，但代码与产物互不相干，上表的对照只比能力不比实现。

## 构建

产物是未签名 HAP：本仓库不分发可执行文件，也不含签名材料。bundleName `com.breeze.ohos`，`compileSdkVersion = compatibleSdkVersion = 26.0.0`，`runtimeOS = HarmonyOS`。

```sh
# 1) 原生引擎 → 编译并拷入 Breeze-ohos/entry/libs/arm64-v8a/libbreeze_qjs_ohos.so
bash scripts/build_rust_ohos.sh --install

# 2) HAP 包 → Breeze-ohos/entry/build/default/outputs/default/entry-default-unsigned.hap
bash scripts/build_hap.sh Breeze-ohos --mode release
```

构建环境变量（SDK、Node、JDK、hvigor 缓存、子进程 shim）集中在 `scripts/build_env.sh`，默认假定工具链在仓库根的 `toolchain/`（不入库），可用 `OHOS_ROOT` 改根路径。NDK clang、sysroot、libclang、mingw 头文件等每台机器都不同的项，由 `node scripts/sync_cargo_config.cjs` 现算后写进 gitignore 的 `breeze_qjs_ohos/.cargo/config.local.toml`（构建脚本每次运行前自动调用），不要手工往 `config.toml` 写绝对路径。

工具链要求（均为实测结论）：

| 组件 | 要求 |
| --- | --- |
| SDK | API 26（`compileSdkVersion 26.0.0`） |
| Node.js | Command Line Tools 自带 `tool/node` |
| JDK | 17（hvigor 的 PackageHap 阶段要 `java`） |
| Rust 宿主 | `nightly-x86_64-pc-windows-gnu`，必须 gnu：msvc 宿主没有 `link.exe`，`-Zbuild-std` 链接必失败 |
| Rust 目标 | `aarch64-unknown-linux-ohos`，配 `-Zbuild-std` |
| C 交叉编译 | NDK clang + OHOS sysroot；宿主侧另需一个 C 编译器（`rquickjs-macro` 会为宿主编一份 QuickJS C 源码） |

改 Rust 前先读 `scripts/build_rust_ohos.sh` 的头部注释，里面写清了四处不可回退的偏差与原生模块装载的几条实测约束（`nm_modname` 命名、显式链 NAPI 库、`oh-package.json5` 声明原生包，以及无 `length` 参数的 NAPI API 只认 NUL 结尾 C 串）。

## 自检

```sh
node scripts/check_imports.cjs     # ArkTS import 图与循环依赖
node scripts/so_names_check.cjs    # 引擎导出名逐项校验（19/19）
node scripts/hap_list.cjs <hap>    # 逐 entry 列大小与 sha256
```

同一份源码连续 clean 重打两次，产物**逐字节相同**（构建是确定性的）。但改动过源码后整包 sha256 必然变化，哪怕语义没变 —— 编译器会在产物里内嵌一份源码哈希，**只改注释也会让它变**，实测过只差 7 个字节而逐 entry 只有 `ets/modules.abc` 一枚变化。所以：判断「是不是同一份代码」比逐 entry sha256 或 abc 里的字符串集合，不要比整包 sha256；只有同源连出两次才用整包 sha256 判可复现。纯 ArkTS 改动后，`.so` 与三个 rawfile 载荷必须逐字节不变。

## 已知限制

本节只列对照表未能表达、或需要额外说明才说得清的决策项。「本项目还有哪项功能没做」一律看[上面的对照表](#应用侧与上游-breeze-的对照)，此处不重复。本项目**处于初始阶段，已知与未知的 BUG 都很多，是否修复、如何修复、何时修复均待定**（修复承诺见[声明与免责](#声明与免责)）。

1. **真机验证只有一台设备**：HUAWEI Mate 80 Pro Max（应用内取到的型号串 = `SGT-AL10`，OpenHarmony 7.0.0.111，API 26）。`module.json5` 的 `deviceTypes` 声明了 phone 与 tablet，但平板与其它机型 / ROM **只编译通过，从未实测**。
2. **启动窗底色只跟随系统色档**：启动画面早于任何 JS 执行，所以手动选深色而系统当前是浅色时，启动窗仍是白底（进入应用后即为你选的深色）。
3. **代理对插件取图无效**：原生层的导出接口里没有代理与 TLS 校验这两档入口，宿主无法把代理配置下发给插件引擎。因此在应用外挂的系统代理不会影响插件取图；上游的代理设置则会改变插件请求的行为，本项目没有对应能力。要在应用内配置代理，必须改动原生层并重编 `.so`。
4. **插件登录态能否持久，取决于插件自己**：宿主提供了持久化通道，但插件是否调用由插件决定；未实现登录接口的插件回「该插件不支持登录」同样属正常行为。杀进程后要不要重登，两种都可能。
5. **升级到分桶版本后各插件需重新登录一次**：早期版本所有插件共用一个配置桶（症状 = A 插件登录后，B 插件的登录页预填出 A 的账号），现已按插件分桶；旧桶里的非凭据项（线路、画质一类）会自动搬到各自插件名下，**凭据一项都不搬**，这是刻意的。登录页对凭据类字段一律不预填。
6. **版本号有两个口径**：应用内显示 `3.0.37` 是刻意与上游**插件契约与行为基线**对齐的版本号，便于逐条追溯行为差异；GitHub Releases 上的 `v1.x.y` 才是本移植项目自己的发布编号，两者互不相干。⚠ 上游已到 v3.1.0，本项目的行为基线仍停在 v3.0.37 —— 应用内那个数字**不代表**已跟进上游最新版，跟进情况一律以上面的对照表为准。
7. **界面语言只有中文**：没有多语言层，也没有切换入口。
